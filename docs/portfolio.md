규칙 하나: **측정한 것과 측정하지 않은 것을 섞지 않는다.** 아래 수치는 전부 실제로 나온 것이고,
미검증 항목은 따로 모아뒀다. 면접에서 단서를 붙여 말하는 쪽이 안 붙이는 쪽보다 세다.

## 1. 핵심 아키텍처 — 제일 자랑할 것

### 문제

Unity 게임은 보통 전투 로직이 엔진에 얽혀 있다. `MonoBehaviour.Update()`, `Rigidbody2D`,
`Physics2D.OverlapCircle`, 프레임레이트 의존. 그러면 이런 게 전부 불가능하다.

- 에디터 없이 규칙을 테스트하는 것
- 봇으로 수천 판을 돌려 밸런스를 재는 것
- **서버가 전투 결과를 검증하는 것**

### 접근

전투 규칙 전체를 **UnityEngine 의존성이 0인 netstandard2.1 라이브러리**로 분리했다.
(`packages/com.petthem.combat-core`)

- `UnityEngine.Vector2` 대신 자체 `Vec2`
- **고정 스텝 1/60초.** 프레임레이트와 무관
- 시드 결정론. 같은 시드 + 같은 입력 = 항상 같은 결과
- 입력 하나(`PlayerInput`)를 넣으면 이벤트 스트림이 나온다

### 결과

**같은 코드가 네 군데서 돈다.**

| 어디 | 무엇 |
|---|---|
| Unity | 게임 |
| .NET 봇 시뮬레이터 | 밸런스 측정 |
| `tools/CoreChecks` | 검사 68개, 에디터 없이 몇 초 |
| `server/PetThem.Server` | 판 가격 산정, (예정) 리플레이 검증 |

### 대가도 같이 말할 것

`Vec2`를 직접 만들어 쓰는 건 확실히 어색하다. 그 어색함이 위의 네 칸을 산 값이다.
**"편한 길을 알면서 안 갔고, 그 대가로 뭘 얻었는지 안다"**가 이 이야기의 핵심이다.

## 2. 면접에서 꺼낼 이야기 (문제 → 접근 → 결과)

### ★ 이빨 없는 테스트를 발견한 것

**제일 추천.** 테스트 품질에 대한 이야기라 직군을 안 탄다.

- **문제**: 보스를 잡은 뒤에 화면에 "보스가 옵니다" 경고가 떴다.
- **원인**: `SecondsToBoss`가 `Math.Max(0, spawnTime - Time)`이라 **보스 등장 후 판이 끝날 때까지
  0이다.** "12초 이하면 경고"는 1분 전에 죽은 보스에도 참이었다.
- **1차 수정**: 두 겹으로 막고 회귀 검사를 썼다. 통과.
- **여기서 멈추지 않았다**: 방어 코드를 빼고 다시 돌려봤다. **여전히 통과했다.**
  검사가 100스텝을 돌린 *뒤에* 확인하는데, 잘못 뜬 경고는 8초면 저절로 사라져서
  검사가 볼 때는 이미 정상으로 돌아와 있었다.
- **결과**: 매 스텝 확인하도록 고쳤고, **방어를 빼면 실패하는 것을 확인**한 뒤 커밋했다.

> **교훈**: 통과하는 테스트가 아니라, **버그를 다시 넣었을 때 실패하는 테스트**여야 한다.
> 그걸 확인하는 건 30초 걸린다.

### ★★ 가정을 쌓기 전에 재본 것 (결정론 측정)

**제일 센 이야기.** 설계 판단 + 측정 + 결과가 다 있고, 예상이 틀린 것까지 있다.

- **배경**: 리플레이 검증 계획 전체가 *"같은 시드 + 같은 입력 = 어디서나 같은 결과"* 하나에
  걸려 있었다. **그런데 아무도 재본 적이 없었다.**
- **접근**: 정해진 한 판(3분, 10,800스텝)을 두 런타임에서 돌리고 일어난 일을 전부
  **원시 비트로** 받아 적어 대조했다. 10진수로 찍으면 형식 차이가 갈라짐처럼 보이거나
  갈라짐을 가린다. 시나리오는 UnityEngine 비의존이라 양쪽에서 **같은 코드**가 돈다.

| 측정 | 결과 |
|---|---|
| 한 판, 모든 이벤트 | **977 / 3,202 줄 다름 (30%)** |
| 40판, 처치 수 | **40 / 40 일치** |
| 40판, 코인 | **38 / 40 일치** (2판 1코인 차) |

**결론**: 완전 일치 검증은 **불가능**하다 — 정직한 플레이어를 거절하게 된다.
허용오차 검증은 **가능하고, 필요한 오차가 작다**. 설계가 바뀌었고, 만들기 전에 바뀌었다.

**그리고 제 예상이 틀렸다.** `Math.Sin`/`Math.Cos`를 범인으로 지목했었다
(IEEE-754가 삼각함수의 정확한 반올림을 요구하지 않으니까). 실제로는 23틱까지 완전 일치였고,
**Sin/Cos를 쓰는 첫 스폰도 비트까지 같았다.** 첫 차이는 `Vec2.Normalized`의
`sqrt(x*x + y*y)` — FMA 접힘이 유력하다. 재보지 않았으면 엉뚱한 곳을 고쳤을 것이다.

> **한계도 같이 말할 것**: x64 두 런타임 비교다. 폰은 IL2CPP가 C++로 컴파일하고
> ARM64는 x64가 아니라 더 벌어질 수 있다. **그 측정은 기기가 필요하고 아직 안 했다.**

### ★★ 측정하다가 서버 버그를 잡은 것

**"양쪽이 똑같이 틀리면 테스트가 통과한다"**의 교과서적 사례.

- **증상**: 첫 대조에서 스폰 위치가 **길이부터** 달랐다(7.3 vs 13.9). 마지막 비트가 아니었다.
- **원인**: `System.Text.Json`은 **public 필드를 읽지 않는다.** `BalanceConfig`는 Unity
  `JsonUtility`에 맞춰 전부 public 필드라, `Deserialize`가 **파일을 통째로 무시하고
  코드 기본값을 돌려주고 있었다.**
- **그런데 서버가 같은 코드로 밸런스 파일을 읽고 있었다.**
  → **서버가 출시 밸런스가 아니라 코드 기본값으로 판 가격을 매기고 있었다.**
- **왜 서버 검사 13개가 못 잡았나**: 검사도 기댓값을 `new BalanceConfig()`로 만들었다.
  **양쪽이 똑같이 틀려서 서로 동의했다.**
- **고친 것**: ① `IncludeFields = true` ② `/health`가 **로드한 밸런스 버전을 보고**
  ③ 검사가 기댓값을 **파일에서** 만들고, **시험 대상(`ServerHost.BalanceJson`)을 공유하지 않는다**
  — 공유했더니 엉뚱한 줄에서 실패하며 원인을 설명하지 못했다.

> **교훈 둘**: 테스트와 코드가 같은 가정을 공유하면 그 가정은 영원히 검증되지 않는다.
> 그리고 **같은 라이브러리의 같은 실수를 두 번** 했다(클라 계약 검사 때 한 번).
> 두 번이면 패턴이라 주석으로 못 박았다.

### ★ 검사가 "통과"를 줬는데 실제 빌드가 죽은 것

**위 이야기와 짝으로 쓰기 좋다.** 하나는 검사가 못 잡은 것, 하나는 검사가 **틀린 답을 준** 것.

- **문제**: `UnityWebRequest`로 업로드 코드를 쓰고 소스 컴파일 검사를 돌렸다.
  **경고 0 / 오류 0.** 그런데 실제 Android 빌드가 `CS1069`로 죽었다.
- **원인**: Unity는 내장 모듈을 **전부** 에디터 폴더에 깔아두지만, 프로젝트가 실제로 쓰는 것은
  `manifest.json`이 정한다. 이 프로젝트는 빌드 크기 때문에 4개만 켜뒀고 `UnityWebRequest`는
  없었다. **꺼진 모듈은 빌드 시점에 존재하지 않는다.**
  그런데 검사는 `UnityEngine/*.dll` — **폴더 전체**를 참조하고 있었다.
  즉 실제로는 못 쓰는 API에 대해 "됩니다"라고 답했다.
- **같은 검사가 전에도 비슷한 실수를 했다.** csproj 주석에 이미 이렇게 적혀 있었다:
  *"폴더 하나를 통째로 빠뜨리는 검사는 검사가 없는 것보다 나쁘다. 믿기 때문이다."*
  이번 건은 그 **한 단계 아래**였다 — 빠뜨린 게 아니라 너무 많이 넣었다.
- **접근**: 와일드카드를 없애고 **켜진 모듈만 이름으로** 참조하게 했다.
  그러면 목록이 두 개가 되므로, **둘이 어긋날 수 없게 검사를 하나 더** 넣었다.
- **여기서 모델이 한 번 틀렸다**: `Font`와 `Input`이 manifest에도 packages-lock에도 없는데
  실제 빌드에는 있었다. 제거 가능한 패키지가 아니라 **엔진 기본 모듈**이었다.
  그래서 "참조 == manifest"가 아니라 **"참조 == manifest ∪ 항상 있는 모듈"**로 고쳤고,
  그 목록은 컴파일러가 하나씩 알려준 것을 경험적으로 채웠다.
- **결과**: **양방향으로** 이빨을 확인했다 —
  켜진 모듈 참조를 **빼면** 실패(빌드에 있는 걸 놓치지 않음),
  꺼진 모듈을 **넣으면** 실패(빌드에 없는 걸 통과시키지 않음).
  두 번째가 원래 없던 쪽이고, 와일드카드가 딱 그 구멍이었다.

> **교훈**: 검사 환경이 실제 빌드 환경과 다르면, 그 검사는 **조용히 틀린 답**을 준다.
> 없는 것보다 나쁘다. 믿기 때문이다.

### ★ 단위 테스트가 못 잡고 실측이 잡은 크래시

- **문제**: 폭발 강화를 추가한 뒤 봇을 12판 돌리다 예외로 죽었다.
- **원인**: 무기 루프가 `for (int i = enemies.Count - 1; i >= 0; i--)`로 역순 순회하면서
  **"피해를 주면 적 하나만 사라진다"**를 전제하고 있었다. 그동안은 맞았다.
  폭발은 한 번에 여러 마리를 지운다 → 목록이 인덱스보다 빨리 줄어 범위 이탈.
  **펀치·레이저·화살·구슬·접촉 피해 루프가 전부 해당됐다.**
- **접근**: 목록 복사본을 순회하고 이미 죽은 적은 건너뛴다.
  버퍼는 **호출 지점마다 따로** 뒀다 — 폭발은 다른 루프의 `Damage` 안에서 일어나므로
  버퍼를 공유하면 바깥 루프의 것을 덮어쓴다.
- **결과**: 회귀 검사로 고정.

> **교훈**: 검사 43개가 통과하고 있었다. **실제로 돌려본 프로그램이 잡았다.**
> 단위 테스트는 "내가 생각한 경우"만 본다.

### ★ null이 아닌 것을 "쓸 수 있다"로 읽은 것

- **문제**: 실기기 APK에서 **글자가 전부 사라졌다.** 한글이 네모로 깨진 게 아니라
  버튼 라벨과 영어까지 전부. 레이아웃·스프라이트·배경은 정상.
- **원인**:
  ```csharp
  Font glyphs = Font.CreateDynamicFontFromOSFont(new[] { "Malgun Gothic", ... }, 32);
  if (glyphs != null) title.font = ... = glyphs;   // null 검사만 했다
  ```
  Android에는 저 이름이 하나도 없는데 **호출은 null이 아닌 Font 객체를 돌려준다.**
  그 객체는 아무 글자도 못 그린다. 그걸 모든 스타일에 씌워서 영어까지 같이 죽었다.
- **접근**: 기기에 **실제로 있는** 폰트 이름을 먼저 묻고(`GetOSInstalledFontNames`),
  만든 폰트가 `HasCharacter('A')`와 `HasCharacter('가')`를 **실제로 통과하는지 증명한 뒤에만** 쓴다.
  - 한글이 안 되고 라틴만 되면 → 그 폰트를 쓰되 **한국어를 끄고 영어로 전환**한다.
    읽을 수 없는 언어를 선택지로 두지 않는다.
  - 전부 실패하면 → **내장 폰트를 그대로 둔다.** 한글은 없지만 영어는 나온다.
  - 시작 화면에 어떤 폰트를 골랐는지 찍는 진단 줄을 넣었다. **내장 폰트로 그려서**,
    고른 폰트가 아무것도 못 그려도 그 줄만은 읽힌다.
- **결과**: 사용자 실기기 확인 — 한글 정상 출력.

> **교훈**: `null`이 아니라는 것은 "쓸 수 있다"가 아니다.
> 그리고 실패는 **"아무것도 없음"이 아니라 "읽을 수 있는 실패"**여야 한다.

### 서버가 가격을 매긴다

- **문제**: 클라이언트가 "코인 460 주세요"라고 보내면 서버는 믿을 방법이 없다.
- **접근**:
  - 판 제출 페이로드에서 **코인 필드를 아예 뺐다.** 클라는 "88킬, 74.5초, 보스 못 잡음"만 말한다.
  - 보상 공식을 코어의 `CombatWorld.CoinsFor` **하나로** 만들었다.
    결과 화면이 보여주는 숫자와 서버가 지급하는 숫자가 같은 함수에서 나온다.
    서버에 공식을 두 번째로 쓰면 반드시 어긋난다.
  - 판의 **이변(난이도 변형)은 클라에게 묻지 않는다.** 이변은 시드에서 굴러 나오고
    코인 수치 자체를 곱하므로, 서버가 시드로 판을 다시 만들어 그 판의 설정을 직접 읽는다.
- **결과**: 전투에 대해 거짓말해도 **임의의 금액이 되지는 않는다.**
- **정직하게 붙일 말**: 처치 수와 시간은 아직 클라의 말이다. 서버가 거르는 건 모양뿐이다
  (음수 처치, 3분을 넘긴 3분 판, 없는 무기). **리플레이 검증이 닫을 구멍**이고 코드와
  README에 그렇게 적었다.

### ★ 계약 검사가 첫 실행에서 잡아낸 것

클라이언트와 서버가 **떨어져 있어서 같은 모양을 두 번 쓸 수밖에 없는** 경우의 이야기.

- **문제**: Unity 클라이언트는 서버 프로젝트(net10.0)를 참조할 수 없다. 그래서 판 제출
  페이로드의 모양이 양쪽에 따로 존재한다. 필드 이름 하나만 어긋나도 서버 쪽에서 기본값으로
  역직렬화되어 **틀린 금액을 지급하고, 아무것도 실패하지 않는다.**
- **접근**: 서버 검사 프로젝트에 **클라이언트 큐 소스를 같이 컴파일**해 넣고,
  클라이언트가 만든 JSON을 서버 계약으로 읽어 필드별로 비교한다.
  그 다음 같은 본문을 **실제로 돌고 있는 서버에 HTTP로** 보내 200이 오는지 본다.
- **결과**: 쓰자마자 잡혔다. `System.Text.Json`은 **public 필드를 직렬화하지 않는다.**
  클라이언트 쪽은 Unity `JsonUtility`에 맞춰 전부 public 필드라 본문이 `{}`로 나갔다.
  `IncludeFields = true`로 Unity가 실제 내보내는 모양을 재현했다.

> 첫 실행에서 잡혔다는 게 요점이다. 이 검사가 없었으면 **필드 이름이 바뀌는 날**
> 조용히 0원을 지급했을 것이다.

### 플레이어가 번 코인을 조용히 버리지 않는 것

- **문제**: 판이 끝났는데 네트워크가 없다. 지하철, 비행기, 서버 점검.
- **접근**: 끝난 판을 **파일에** 쌓고(변수가 아니라) 보낼 수 있게 되면 보낸다. 며칠 뒤
  다른 네트워크여도 된다. 재시도 간격은 2초에서 두 배씩 늘어 **5분에서 멈춘다** —
  밤새 쌓인 큐가 아침에 즉시 나가야 하므로 무한정 벌리지 않는다.
- **핵심 판단**: HTTP 응답을 **"아직 정해지지 않음"과 "영원히 안 됨"**으로 가른다.
  - 타임아웃·429·5xx → 서버가 아직 답을 안 한 것. **계속 들고 있는다**
  - 400 → 서버가 읽고 거절한 것. 다시 보내도 같은 거절이라 **들고 있으면 무한 루프**
  - 401 → 둘 다 아니다. **판은 멀쩡하고 세션이 문제**다. 토큰만 버리고 판은 줄을 다시 선다
- **버려지는 경우엔 이유를 남긴다.** 설정 화면에 표시한다. 삼키지 않는다.

> 클라이언트가 고집스러울 수 있는 건 **서버가 멱등이기 때문**이다.
> 양쪽이 한 설계고 기계 두 대에 나뉘어 있을 뿐이다.

### ★ 설계한 이음매가 실제로 값을 한 것 (메모리 → SQLite)

**"추상화를 왜 뒀냐"에 대한 답이 되는 이야기.** 보통은 말로만 하는데 여기는 결과가 있다.

- **배경**: 서버 저장이 메모리뿐이라 프로세스를 껐다 켜면 전원 코인이 사라졌다.
- **`IProfileStore`를 불러오기/저장하기 쌍이 아니라 트랜잭션 경계로 설계해뒀었다.**
  "이 판이 계산됐나, 아니면 코인 더하고 표시" — 세 단계가 엇갈리면 안 되니까.
- **결과: 엔드포인트가 한 줄도 안 바뀌었다.** 잠금이 트랜잭션이 됐을 뿐이다.
- **멱등성이 코드 검사에서 DB 제약이 됐다.** `counted_runs`의 PK가 `(player_id, run_id)`고,
  지급 여부를 묻지 않는다 — `INSERT OR IGNORE`의 **삽입된 행 수가 곧 답**이다.
  "이미 계산됐나?"를 묻고 계산하는 코드에는 두 질문 사이 틈이 있지만, 삽입에는 틈이 없다.

**첫 시도가 동시 요청에서 깨졌다**: 연결 하나를 공유했더니 업로드 두 개가 동시에 오는 순간
죽었다. SQLite는 이미 트랜잭션 중인 연결에서 두 번째를 못 연다. 요청마다 연결을 열고,
쓰기는 **`BEGIN IMMEDIATE`**로 바꿨다 — deferred면 읽기 잠금을 먼저 잡고 승격을 시도하는데,
둘이 동시에 승격하려 하면 **어떤 타임아웃으로도 안 풀리는 교착**이다.

> **그리고 여기서 과장하지 않은 게 중요하다.** 8개 동시 업로드가 한 번만 지급되는 걸
> 확인했는데, `deferred: true`로 바꿔도 **여전히 통과한다.** 즉 트랜잭션 직렬화와 기본 키가
> 둘 다 지키고 있고 어느 쪽이 실제로 버티는지는 이 검사로 안 갈린다.
> **측정이 아니라 이중 방어다.** 주석과 문서에 그렇게 적었다.

**검사로 고정한 것**: 같은 판을 3번 보내도 코인은 1회분, `runsFinished`는 1.
8개를 동시에 보내도 정확히 1개만 첫 지급으로 처리된다.
서버를 재시작한 뒤에 또 보내도 마찬가지다.

### 기본값을 뒤집지 않은 것

- **문제**: 판마다 난이도 변형(이변)을 넣으면 **기존 검사 49개와 봇 전부의 수치가
  조용히 무의미해진다.** 전부 이변 없는 조건으로 작성됐기 때문이다.
- **접근**: `enableTwists` 기본값을 `false`로 두고 **게임만 `true`를 넘긴다.**
  그리고 **그 기본값 자체를 검사가 고정한다** (시드 40개가 전부 `Calm`이어야 한다).
- **결과**: 새 기능이 기존 측정값을 오염시키지 않는다.

> 라이브러리에 기능을 추가할 때 기본 동작을 바꾸지 않는 것, 그걸 테스트로 못 박는 것.

### 버튼 하나가 전투를 바꿀 뻔한 것 (다시 돌리기)

**난수 스트림 분리가 왜 중요한지 실제로 드러난 사례.**

- **문제**: 레벨업 카드 손패가 마음에 안 들면 다시 뽑는 기능을 넣었다.
- **함정**: 다시 돌리기에 **전용 난수 스트림**을 주는 게 자연스러워 보였다.
  그런데 그러면 "버튼을 눌렀는지"가 난수 소비량을 바꾸고,
  **적 스폰 위치와 보스 기술 순서가 달라진다.**
- **접근**: 첫 배분과 **같은 스트림**에서 뽑게 했다. 다시 돌리기도 강화 뽑기니까.
- **검사로 고정**: 같은 시드로 두 판을 돌리되 한쪽만 매 레벨 2번씩 다시 돌린다.
  **스폰·보스 이벤트 기록이 바이트 단위로 같아야 한다.**

> 재현성이 걸린 게임에서는 **"플레이어가 뭘 눌렀는지가 세계를 바꾸면 안 되는 곳"**이 있다.
> 리플레이 검증을 하려면 특히 그렇다.

### 난수 스트림을 분리한 것

크리티컬을 굴렸다고 적 등장 위치나 다음 강화 카드가 달라지면 재현성이 깨진다.
**독립 스트림 5개**(스폰 / 성장 / 효과 / 보스 / 이변)를 쓴다.
크리티컬 확률을 조정해도 같은 시드의 스폰·카드·보스 기술 순서가 그대로다.

### 화면과 실제가 어긋날 수 없게 만든 것

활 게이지, 조준 미리보기, 실제 발사가 **`CombatWorld.DrawPower` 같은 함수**를 쓴다.
"게이지가 60% 찼는데 약하게 나갔다"가 구조적으로 불가능하다.

같은 원칙으로, 펀치 이펙트 링을 실제 사거리와 일치시켰다. 이전에는 보이는 원보다 판정이 넓었다.

> "봇이 답할 수 있는 질문과 없는 질문을 구분했습니다"가 세다.

## 5. 정직하게 말할 약점

면접에서 먼저 꺼내는 편이 낫다.

- **리플레이 검증은 아직 없다.** 결정론은 쟀고(위), 설계는 허용오차 방식으로 정해졌다.
- **로그인이 게스트뿐이다.** 신원 확인이 없다.
- **로컬 저장이 아직 정본이다.** 서버는 같은 숫자를 받지만 권위는 아직 아니다.
  저장과 로그인이 없는 상태에서 권위를 넘기면 프로세스가 죽을 때마다 코인이 사라진다.
- **클라이언트와 서버가 같이 도는 것을 아직 실제로 못 봤다.** 양쪽 검사는 통과하지만
  Unity가 실제로 이 서버를 호출한 적은 없다.
- **손맛을 사람이 거의 확인하지 못했다.** 확인된 건 한글 표시와 소리, 코치 가독성뿐이다.
- MCP와 밸런스 실험실은 **의도적으로 보류**했다. 게임 완성이 먼저라고 판단했다.

## 0.18.0 — 유한 경기장에서 이동형 월드로 확장

**문제:** 플레이어 이동 제한만 없애면 화살이 원점 기준 경계에서 사라지고, 느린 적들이 뒤에 쌓여 개체 수 상한을 채우며, 배경이 끝난다.

**접근:** 공통 코어의 endlessWorld 옵션으로 경계·스폰·투사체 수명을 함께 처리했다. 기본 false로 기존 경기장 규칙을 유지하고 배포 JSON에서 활성화했다. 일반 적 재배치는 처치/보상과 분리하고 보스를 제외했다. Unity는 추적 카메라와 재사용 지형 청크만 담당한다. 세 지형 테마는 별도 좌표 난수로 꾸미므로 전투 재현성에 영향을 주지 않는다.

**검증:** 새 검사 3개 포함 게임 63개, 서버 HTTP 10개, 실험실 회귀 14개 통과. 3,600스텝 이동에서 원점 경계 통과·적 수 상한·동일 시드 위치 일치·재배치 시 보상 없음, 원점 밖 화살의 발사/소멸, 멀리 이동한 플레이어 주변의 보스 생성을 검사했다. 소스 컴파일 오류·경고 0.

**한계:** 3분 판 구조를 유지하는 무경계 이동형 전투장으로, 퀘스트/영속 월드를 갖춘 오픈월드 게임은 아니다. 발·앞발 분리 렌더러를 추가한 성능은 실기기에서 아직 측정하지 않았다. UnityWebRequest와 서버의 실제 동시 실행도 별도로 남아 있다.
