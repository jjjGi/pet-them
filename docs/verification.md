## 2026-09-16 — 주무기 3종 (게임 0.3.0)

전투 규칙 검사 **22개 통과** (기존 17개 + 무기 5개). Unity 런타임 소스 컴파일 경고·오류 0.

### 새로 확인한 항목

18. 화살이 날아가고, 관통 상한만큼만 피해를 주며, 쿨다운 동안 버튼을 계속 눌러도 추가 발사되지 않는다.
19. 화살은 누르는 동안 조준만 하고 떼는 순간 한 발만 나간다. 느린 화살이 적에 겹쳐 있어도 같은 적에게 두 번 기록되지 않는다.
20. 레이저는 플레이어 앞쪽만 태운다. 열이 100이 되면 잠기고, 버튼을 계속 눌러도 피해가 없으며, **열이 완전히 0이 될 때까지** 복구되지 않는다.
21. 제시되는 강화는 판을 시작한 무기의 것뿐이다. 세 무기 각각 6레벨까지 확인했다.
22. 무기 수치가 유효성 검사를 받는다. arrowPierce 0, laserRange 0, arrowSpeed NaN은 거부된다.

### 구현 중 고친 것

**릴리스로 발사할 때 자동 조준이 걸리지 않았다.** 조준 보정이 `input.punch`만 보고 있어서,
드래그 없이 탭했다 떼는 경우 화살이 항상 초기 방향(오른쪽)으로 나갔다.
모바일에서 탭으로 쏘는 플레이어에게 그대로 드러나는 문제였다. 발사 여부를 먼저 계산해 조준에 넘기도록 바꿨다.

**일시정지·강화 선택 중 드래그가 끊기면 재개 첫 스텝에서 화살이 저절로 나갔다.**
코어가 "누르고 있다가 뗐다"로 읽기 때문이다. `CancelHeldAttack()`을 추가하고 입력 초기화에서 호출한다.

나중에 상한을 하나만 더 추가해도 게임이 죽는 코드였다. 빈 목록에서 빠져나가도록 막았다.

### 설계 결정

- 무기는 판 시작 시 1개만 고르고 도중에 바꿀 수 없다. PROJECT.md 3절의 기준 그대로다.

- 레이저 조준은 자동 보정을 하지 않는다. 빔이 저절로 표적을 옮기면 플레이어가 조준하는 무기가 아니게 된다.
- 화살은 발사한 스텝에 이미 명중할 수 있다. 적이 몰려 있으면 흔한 일이라 검사도 그 전제로 작성했다.
- 과열 중에는 냉각도 느려진다(`laserOverheatPenalty`). 과열의 대가가 실제 공백이 되도록 한 것이다.

### 아직 확인하지 않은 항목

- 0.3.0 Android APK 빌드와 실기기.
- 무기별 밸런스. 수치는 초기값이며 사람의 플레이 전에는 조정하지 않는다.
- 봇 정책은 여전히 펀치만 사용한다. 화살·레이저의 봇 실험은 정책 추가 후에 가능하다.

### 분류를 만든 이유

카드 22종을 이름만 늘어놓으면 고르기가 더 어려워진다. 무기·펫·동료·발동·몸 다섯 갈래로 나누고
**카드 옆에 색 띠와 분류 이름**을 붙였다. 글을 읽기 전에 "이건 동료 카드구나"가 먼저 보이게 하기 위해서다.

랭크는 숫자 대신 점(●●○○○)으로 표시한다. 한눈에 들어오는 쪽이 낫다.

### 일시정지 화면의 빌드

일시정지나 판이 끝났을 때 **무기 + 펫 + 레벨**과 지금까지 고른 강화를 분류별로 한 줄씩 보여준다.

10레벨쯤 되면 뭘 골랐는지 기억이 안 나는데, 그 선택이 레벨업 화면의 전부다.
분류별로 묶어서 목록이 아니라 **빌드로 읽히게** 했다.

### 검사가 잡은 크래시

**폭발이 실제 크래시를 만들었다.**

기존 무기 루프는 `for (int i = enemies.Count - 1; i >= 0; i--)`로 적 목록을 역순으로 돌았다.
피해를 주면 **그 적 하나만** 사라진다는 전제였고, 그동안은 맞았다.

폭발은 한 번에 여러 적을 제거한다. 목록이 인덱스보다 빨리 줄어들어 범위를 벗어난다.
펀치·레이저·화살·구슬·접촉 피해 루프가 전부 해당됐다.

발견은 검사가 아니라 **실측 프로그램**이었다. 12판을 돌리다 예외로 죽었다.
이제 목록 복사본을 돌고 이미 죽은 적은 건너뛴다. 검사 하나를 추가해 고정했다.

버퍼는 호출 지점마다 따로 둔다. 폭발은 다른 루프의 `Damage` 안에서 일어나므로
버퍼를 공유하면 바깥 루프의 것을 덮어쓴다.

### 크리티컬은 별도 난수 스트림

급소를 찍었다고 적 등장 위치나 다음 카드가 달라지면 안 된다. 전용 스트림을 쓴다.
같은 시드는 같은 크리티컬을 낸다. 검사로 확인했다.

폭발과 반격은 크리티컬을 굴리지 않는다. 타격의 결과이지 타격이 아니기 때문이다.

### 측정: 한 판에 나오는 카드 수

시드 1~12, 후퇴하며 공격하는 봇.

| 무기 | 선택 횟수 | 등장한 카드 종류 |
| --- | --- | --- |
| 펀치 | 127 | 15 |
| 레이저 | 16 | 15 |

22종 중 15종이 등장한다. 나머지 7종은 다른 무기·펫 전용이라 그 판에서는 원래 나오지 않는다.
레이저의 선택 횟수가 적은 것은 앞서 기록한 봇 조준 결함 때문이며 밸런스와 무관하다.

### 검사를 고친 부분

풀이 14종에서 22종으로 커지면서, 특정 카드가 뽑히기를 기대하던 기존 검사 두 개가 운에 의존하게 됐다.

## 2026-09-18 — Android에서 글자가 하나도 나오지 않음 (0.11.2)

사용자가 0.11.1 APK를 설치하고 스크린샷을 보냈다. **글자가 전혀 없다.**
한글이 네모로 깨진 것이 아니라, 버튼 라벨과 영어를 포함해 **모든 텍스트가 사라졌다.**
레이아웃, 카드, 색 띠, 스프라이트, 배경은 정상이었다.

### 원인

폰트 대체 코드가 이랬다.

~~~csharp
Font glyphs = Font.CreateDynamicFontFromOSFont(new[] { "Malgun Gothic", ... }, 32);
if (glyphs != null) title.font = ... = glyphs;
~~~

`null` 검사만 하고 있었다. Android에는 저 이름들이 하나도 없는데
**호출은 null이 아닌 Font 객체를 돌려준다.** 그 객체는 아무 글자도 그리지 못한다.
그것을 모든 스타일에 씌워서 영어까지 같이 사라졌다.

내장 폰트를 유지했다면 최소한 영어는 보였을 것이다. `null`이 아니라는 것을
"쓸 수 있다"로 해석한 것이 잘못이었다.

### 고친 방법

1. `Font.GetOSInstalledFontNames()`로 **기기에 실제로 있는 이름**을 먼저 묻는다.
2. 선호 목록과 부분 일치하는 이름만 시도한다.
3. 만든 폰트가 `HasCharacter('A')`와 `HasCharacter('가')`를 실제로 통과하는지 확인한다.
4. 한글이 안 되고 라틴만 되면 그 폰트를 쓰되 **한국어를 끄고 영어로 전환**한다.
   읽을 수 없는 언어를 선택지로 두지 않는다. 언어 전환 버튼도 숨긴다.
5. 전부 실패하면 **내장 폰트를 그대로 둔다.** 한글은 없지만 영어는 나온다.

목록 조회가 비어 있는 Android 버전도 있어서, 그 경우 이름을 직접 시도하는 단계를 하나 더 두었다.
다만 이때도 **검증을 통과해야만** 사용한다.

### 진단 줄을 넣었다

시작 화면 맨 아래에 어떤 폰트를 골랐는지, 기기가 보고한 폰트가 몇 개이고 앞 6개가 무엇인지 찍는다.
**이 줄만은 내장 폰트로 그린다.** 고른 폰트가 글자를 못 그려도 이 줄은 살아남아야 하기 때문이다.

케이블 없이 원격으로 폰 상태를 알 방법이 이것뿐이다.

### 아직 해결되지 않은 것

**Android에서 한글이 나오는지는 여전히 모른다.** 이 변경은 "아무것도 안 보이는" 상태를 없애고,
기기가 무엇을 갖고 있는지 알아내기 위한 것이다.

진단 줄을 확인한 뒤에야 다음을 정할 수 있다.

- 기기가 Hangul 폰트를 보고하면 → 이 수정으로 해결.
- 보고하지 않으면 → 폰트 파일을 APK에 넣어야 한다.
  `NotoSansKR-VF.ttf`가 후보이고 SIL OFL이라 재배포는 가능하지만,
  **10 MB이고 가변 폰트라 Unity에서 검증되지 않았다.** 사용자와 상의할 사항이다.
  `malgun.ttf`는 Microsoft 독점이라 재배포할 수 없다.

### 사전 검증이 Editor 폴더를 빠뜨리고 있었다

위 폰트 수정을 넣고 "컴파일 통과"를 확인한 뒤 APK를 빌드했는데 **실패했다.**
`PrototypeSetup.cs`가 `Texts`를 참조하는데 `using PetThem.Game;`이 없었다.

원인은 사전 검증 프로젝트가 `Assets/Scripts/*.cs`만 컴파일하고 **`Assets/Editor`는 건드리지 않았다**는 것이다.
그래서 "경고 0 / 오류 0"이라고 보고했다. 한 폴더를 통째로 빠뜨린 검사는
없는 것보다 나쁘다. 믿게 되기 때문이다.

세 가지를 바꿨다.

1. 누락된 `using` 추가.
2. 검사 프로젝트를 `experiments/`(Git 제외)에서 **`tools/UnitySourceCheck/`로 옮겨 버전 관리에 넣었다.**
   이전에는 이 검사가 이 PC에만 있었고 다른 사람은 쓸 수 없었다.
   Unity 경로는 `UNITY_EDITOR_ROOT`로 바꿀 수 있고, 없으면 이유를 말하며 멈춘다.
3. `Assets/Editor/*.cs`도 컴파일 대상에 넣고, `scripts/check.ps1`에서 함께 실행한다.
   Unity가 없으면 건너뛰되 **건너뛴다고 출력한다.** 조용히 통과하지 않는다.

이 과정에서 Codex가 넣은 `ClayArtImporter.cs`도 검사 범위에 들어왔다. 이전에는 아무도 컴파일하지 않았다.

참조에서 단일 `UnityEditor.dll`은 뺐다. 그 옆 `UnityEngine/` 폴더에 `UnityEditor.*Module.dll`이
모두 들어 있어서, 둘 다 참조하면 `MenuItem` 같은 타입이 중복 정의로 잡힌다.

## 0.12.0 — 보스 패턴

### 이전 항목 마감: Android 한글

위 "아직 해결되지 않은 것"은 **해결됐다.** 사용자가 실기기에서 확인했다: 한글이 정상 출력된다.
기기가 Hangul 폰트를 보고했고, 폰트 파일을 APK에 넣을 필요는 없었다.

### 보스가 무엇을 하게 됐는가

이전 보스는 다른 적과 똑같이 플레이어를 향해 걸어오기만 했다. 체력만 큰 잡몹이었다.
이제 `CombatBoss.cs`의 상태 기계가 돈다.

| 기술 | 확률 | 하는 일 |
|---|---|---|
| 돌진 Charge | 42% | `bossChargeSpeed` 11로 직선 돌진, 닿으면 38 피해 |
| 내려찍기 Slam | 33% | 반경 4.2 안을 한 번에 32 피해 |
| 소환 Summon | 25% | 자기 주위에 Runner 4마리를 원형으로 |

모든 기술 앞에 `bossTelegraph` 0.85초의 예고가 붙는다. 예고 없는 피해는 없다.

### 피할 수 있는 기술인가

돌진 방향은 **예고가 시작될 때** 고정된다(`BeginTelegraph`). 예고가 끝날 때가 아니다.
그래서 옆으로 비키면 빗나간다. 이게 뒤집히면 회피가 불가능해지므로 검사로 고정했다.

보스 이동 속도는 1.05, 플레이어는 4.5다. 보스는 플레이어를 걸어서 절대 따라잡을 수 없다.
돌진만이 보스가 거리를 좁히는 수단이다.

### 측정

봇 12판씩, 자동 조준, 주먹 무기:

| 펫 | 처치 | 시간승 | 사망 | 기술 명중률 |
|---|---|---|---|---|
| 모치 | 5 | 4 | 3 | 37/117 (32%) |
| 보리 | 4 | 4 | 4 | 39/119 (33%) |
| 코코 | 7 | 5 | 0 | 41/121 (34%) |

봇은 회피를 전혀 시도하지 않는다. **그런데도 3분의 2는 빗나간다.**
예고 시간이 충분하다는 뜻이고, 사람이 보고 피하면 명중률은 이보다 훨씬 낮아야 한다.
너무 낮아서 기술이 무의미해지는지는 사람이 해봐야 안다.

### 봇 결과 중 믿으면 안 되는 것

**활 봇의 보스전 결과는 무효다.** 12판 전부 보스 등장 후 10초 안에 죽는데,
사망 위치가 6판 모두 정확히 같은 구석 (13.6, 7.6)이었다.

봇은 "가장 가까운 적의 반대 방향"으로만 도망친다. 그래서 벽으로 직진하다 구석에 갇히고,
갇힌 뒤에는 도망 방향이 계속 벽을 향해서 빠져나오지 못한다. 보스는 그 자리에서 밀착 피해를 준다.
주먹은 자기를 가둔 적을 때려죽여서 빠져나오지만 활은 그러지 못한다.

즉 **보스가 강해서가 아니라 봇이 벽에 처박혀서** 죽는다. 이 수치로 활을 강화하면 안 된다.
레이저 봇 결과가 무효인 것(자동 조준이 없어 봇이 조준값을 주지 않으면 빔이 계속 오른쪽을 향한다)과 같은 종류의 함정이다.

패턴을 껐을 때와 켰을 때를 비교해서 확인했다. 활 봇은 **패턴이 아예 없어도** 3.6초 만에 죽는다.
패턴을 켜면 오히려 8.7초로 늘어나는데, 보스가 예고·내려찍기 동안 멈춰 서기 때문이다.
새로 만든 패턴이 활을 불리하게 만든 것이 아니라, 원래 있던 문제다.

### 검사 3개 추가 (총 46개)

1. **모든 보스 기술은 착탄 전에 예고된다** — 어떤 기술의 피해든, 그 기술의 `boss_telegraph` 이후
   최소 `bossTelegraph` 틱이 지나야 도착한다. 처음엔 "예고 봤음" 플래그를 `boss_move`에서 껐다가
   실패했다. 돌진 피해는 `boss_move` **뒤에** 들어오기 때문이다.
2. **돌진은 예고 시점에 조준되고 그 뒤로는 따라오지 않는다.**
3. **격노하면 빨라지고, 소환된 적은 소환으로 집계된다.** 잘못된 보스 설정은 거부한다.

### 무작위 스트림 분리

보스 기술 선택은 `bossRandom`이라는 **독립 스트림**을 쓴다. 기존 `random`(스폰),
`progressionRandom`(강화 카드), `effectRandom`(치명타)과 섞이지 않는다.
보스 기술 확률을 건드려도 같은 시드의 웨이브 구성과 카드 목록은 그대로다.
이게 아니었으면 보스 조정 한 번에 모든 봇 측정값이 무의미해진다.

### 화면 표시

- 바닥에 예고 도형: 돌진은 **레인**(진행 방향·길이 `chargeSpeed × chargeSeconds`),
  내려찍기와 소환은 **원**. 예고가 진행될수록 커진다.
  `sortingOrder 2`로 생물보다 아래에 그려서 적을 가리지 않는다.
- 보스 체력바 위에 기술 이름(`돌진!` / `내려찍기!` / `부른다!`)을 예고 중에만 띄운다.
  도형은 *어디*를, 글자는 *무엇*을 알려준다.
- 체력 35% 아래로 내려가면 체력바 옆에 `격노`가 붙는다. 기술 간격이 0.62배로 줄어든다.

## 0.14.0 — 이변과 웨이브 구성

### 문제

0.13.0까지의 판은 **매번 똑같았다.** 무기·펫·강화 카드만 다를 뿐,
적 구성도 등장 속도도 보스 시각도 고정이었다. 로그라이트인데 판을 거듭할 이유가 약했다.

### 웨이브마다 적 구성이 달라진다

이전 `Spawn()`은 Runner 28% / Brute `bruteShare` / 나머지 Grunt로 **웨이브와 무관하게 고정**이었다.
웨이브가 올라가면 스폰 간격과 체력 배수만 변했다. 3분째가 1분째와 같은 싸움이었다.

이제 비율이 웨이브를 따라 올라간다.

- 1웨이브: **브루트가 아예 없다.** Runner는 최종 비율의 30%.
- `mixWaves`(5) 웨이브에 도달하면 설정된 최종 비율 전부.

`runnerShare`(0.34)와 `mixWaves`(5)를 설정에 추가했다. `bruteShare`는 이제 "항상 이 비율"이 아니라
**"도달하는 비율"**로 의미가 바뀌었다. 둘의 합이 0.95를 넘으면 Grunt가 사라지므로 설정을 거부한다.

### 판마다 조건이 하나 붙는다

`CombatTwist.cs` 신설. 판이 시작될 때 6종 중 하나가 정해지고 끝까지 고정된다.

| 이변 | 하는 일 | 코인 |
|---|---|---|
| 평범한 날 | 없음 | — |
| 우글우글 | 스폰 간격 ×0.62, 적 체력 ×0.82 | ×1.25 |
| 발 빠른 무리 | 적 이동속도 ×1.28 | ×1.25 |
| 단단한 껍질 | 적 체력 ×1.4, 스폰 간격 ×1.18 | ×1.3 |
| 이른 방문 | 보스 등장 120초 → 72초 | ×1.35 |
| 매서운 이빨 | 접촉·돌진·내려찍기 피해 ×1.35 | ×1.4 |

**코인 배수를 따로 만들지 않았다.** `coinsPerKill` 같은 설정값 자체에 곱하므로,
보상 경로가 두 개로 갈라져서 서로 어긋날 여지가 없다.

이변은 **생성자에서 설정 복사본에 미리 접어 넣는다.** 그 아래 코드는 이변의 존재를 모른다.
강화의 "처음 위력의 20%"도 이변이 적용된 값 기준이라, 어떤 판에서든 같은 비중을 갖는다.

### 기본값은 꺼져 있다

`enableTwists`는 **기본 false**다. 기존 호출자 — 검사 49개와 봇 전부 — 는 이변 없는 수치로 작성됐다.
기본값이 뒤집히면 그것들의 결과가 조용히 무의미해진다. 게임만 `true`를 넘긴다.
검사가 이 기본값을 직접 고정한다(시드 40개 전부 `Calm`이어야 한다).

무작위도 `twistRandom` 독립 스트림이다. 이변을 추가하거나 순서를 바꿔도
같은 시드의 스폰·카드·치명타·보스 기술은 그대로다.

### 측정 (펀치+모찌 봇, 이변별 10판)

| 이변 | 평균 생존 | 처치 | 코인 | 보스처치 / 시간승 / 사망 |
|---|---|---|---|---|
| 평범한 날 | 160.6s | 212 | 460 | 5 / 1 / 4 |
| 우글우글 | 166.2s | 352 | 797 | 7 / 2 / **1** |
| 발 빠른 무리 | 152.3s | 194 | 517 | 3 / 1 / **6** |
| 단단한 껍질 | 161.1s | 186 | 523 | 5 / 2 / 3 |
| 이른 방문 | 113.1s | 136 | 407 | 6 / 0 / 4 |
| 매서운 이빨 | 154.6s | 197 | 580 | 3 / 1 / **6** |

여섯 개가 서로 다른 판이 된다는 것은 확인됐다. 생존 시간, 처치 수, 최대 동시 적 수가 모두 갈린다.

### 지켜봐야 할 것 — 우글우글

**우글우글이 코인을 25% 더 주면서 이 봇에게는 가장 쉽다**(사망 1회, 평범한 날은 4회).
적이 약해지는 만큼 펀치의 범위 공격이 그대로 이득을 보기 때문이다.

이것이 문제인지는 아직 모른다. 화살처럼 단일 대상 무기로는 반대로 가장 어려울 수 있고,
그렇다면 "무기에 따라 유불리가 갈리는 이변"이라 오히려 의도한 설계다.
**봇은 펀치만 쓰므로 이 질문에 답하지 못한다.** 사람이 활·레이저로 우글우글을 해 봐야 안다.

### 화살 미리보기가 캐릭터를 따라간다

사용자 보고: "움직이면서 당기면 미리보기가 안 따라온다."

미리보기 전체가 **손가락이 처음 닿은 화면 좌표**에 그려지고 있었다. 화살은 캐릭터에서 나가는데
방향 표시는 엄지 옆에 남아 있었고, 걸으면서 당기면 화살이 출발하지도 않을 지점에서 뻗어 나갔다.

둘로 나눴다.

- **조작인 것**(고리, 당겨진 시위, 힘 게이지)은 엄지 밑에 그대로 둔다. 손가락이 쥐고 있는 물건이다.
- **답인 것**(날아갈 방향 점 줄기)은 `WorldToScreenPoint`로 **캐릭터 위치에서** 그린다.

방향은 당김 벡터를 다시 계산하지 않고 `world.Facing`을 쓴다. 실제 발사가 쓰는 바로 그 값이라
미리보기가 실제 발사와 어긋날 수 없다. `DrawPower`를 게이지와 발사가 공유하는 것과 같은 원칙이다.

## 0.15.0 — 첫 30초를 가르친다

### 문제

**게임에 설명이 하나도 없었다.** 시작 화면의 `StartControls` 한 줄과 전투 중 화면 구석의
`MoveHint` 한 줄이 전부다. 둘 다 "왼쪽 엄지로 이동"까지만 말한다.

가장 큰 구멍은 활이다. 0.9.0에서 활은 클릭 발사에서 **당겼다 놓는 제스처**로 바뀌었고,
`arrowMinDraw`(0.25) 미만으로 당기면 **발사되지 않고 쿨다운도 돌지 않는다.**
화면에서 아무 일도 일어나지 않고, 왜 아무 일도 일어나지 않는지 말해 주는 것도 없다.
활을 고른 첫 플레이어는 무기가 고장 났다고 판단할 수 있다.

### 튜토리얼이 아니라 코치다

`game/Assets/Scripts/Coach.cs` 신설. 판을 멈추지 않고, 닫을 것도 없고,
**이미 아는 플레이어는 그냥 플레이하는 것만으로 모든 수업을 통과하고 한 글자도 읽지 않는다.**

| 수업 | 언제 뜨는가 | 언제 끝나는가 |
|---|---|---|
| 이동 | 판 시작 | 3m 걸으면 |
| 공격 (무기별 3종) | 이동을 배우면 | 3처치 |
| 당기기 (활 전용) | 발사 안 되는 당김 2회 | 화살이 실제로 나가면 |
| 강화 | 첫 강화를 고르면 | 6초 후 |
| 보스 | 보스 12초 전 | 8초 후 |

**전투 코어는 건드리지 않았다.** 대본 구역도, 순한 첫 웨이브도, 강제 정지도 없다.
플레이어가 배우는 게임과 봇이 재는 게임이 같은 게임이어야 하고,
수업이 설명하는 규칙과 실제 규칙이 어긋날 여지도 없어야 한다.

### 당기기 수업이 이 작업의 핵심이다

발사되지 않은 당김을 세는 판정은 `world.DrawPower(drawAmount) <= 0`이다.
**실제로 화살을 쏘는 바로 그 함수다.** 게이지·미리보기가 `DrawPower`를 공유하는 것과 같은 원칙으로,
"안 나갔다"는 코치의 판단이 실제 발사 결과와 어긋날 수 없다.
한 번은 실수로 보고 넘기고, 두 번째에 "더 당기세요. 살짝 누르는 것은 발사가 아닙니다"가 뜬다.

이 수업만 이동 수업보다 우선순위가 높다. 지금 실패하고 있는 사람에게 걷는 법을 먼저 말할 이유가 없다.

### UnityEngine 비의존 — 검사가 가능한 이유

`Texts.cs`·`PlayerProfile.cs`와 같은 방침이다. 튜토리얼의 가치는 전적으로
**맞는 순간에 뜨는가**에 달려 있는데, 그건 에디터 없이 돌릴 수 있어야 검증된다.
`Coach.cs`를 `tools/CoreChecks`에 컴파일해 넣었다.

새 검사 4개:

- 한 번에 하나만 가르치고, 배우면 멈춘다. 제자리에 서 있으면 600스텝이 지나도 이동 수업이 안 끝난다.
  잘게 나눠 걸어도 합계가 같은 거리에서(±한 걸음) 끝난다.
- 활 수업은 활에만 뜬다. 펀치·레이저로 아무리 짧게 눌러도 안 뜬다.
  화살이 한 번 나가면 이후 10번 짧게 당겨도 다시 안 뜬다.
- 공지(강화·보스)는 떴다가 시간이 지나면 사라지고, 상시 수업보다 우선한다.
  두 번째 강화는 수업을 되살리지 않는다. 보스가 이미 서 있으면 뒤늦게 경고하지 않는다.
- 배운 것은 판 사이에 남는다. 10초 만에 껐다 켜도 남은 수업부터 이어진다.
  나중 버전이 쓴 저장값(`int.MaxValue`, `-1`)이 이 버전의 수업을 조용히 끄지 못한다.

번역 검사에 `CoachLine`(수업 × 무기 전부)과 `CoachReplay`를 추가했다.
공격 수업은 무기마다 다르므로 수업별이 아니라 **쌍별로** 다 채워졌는지 본다.

### 작업 중 잡은 버그 — 시체 위에 뜨는 보스 경고

`CombatWorld.SecondsToBoss`는 `Math.Max(0, bossSpawnTime - Time)`이다. **보스가 등장한 뒤로는 판이 끝날 때까지 0이다.**
보스 경고를 "12초 이하면 뜬다"로만 쓰면, 보스를 **잡은 뒤**에도 조건이 계속 참이라
시체 위에 "보스가 옵니다"가 뜬다. 화면의 기존 보스 카운트다운은 `!world.BossDefeated`로 막고 있었고,
코치에는 그 조건이 없었다.

두 겹으로 막았다.

- 게임이 `world.Boss != null || world.BossDefeated`를 넘긴다. 등장했거나 이미 지나갔거나.
- 코치가 `secondsToBoss > 0`을 **추가로** 요구한다. 0은 "곧 온다"가 아니라 "왔다" 또는 "왔다 갔다"이므로,
  호출하는 쪽이 도착 보고를 빠뜨려도 시체 위에 뜨지 않는다.

**처음 쓴 회귀 검사는 이 버그를 못 잡았다.** 100스텝을 돌린 *뒤에* 확인했는데,
잘못 뜬 경고는 8초면 저절로 사라지므로 검사가 볼 때는 이미 정상으로 돌아와 있었다.
방어 코드를 빼고 돌려 보고서야 알았다. 지금은 **매 스텝** 확인한다.
빼면 실패하는 것을 확인했다.

### 저장과 되돌리기

`PlayerPrefs`의 `coach.learned` 비트마스크. 오디오 설정과 같은 방식이고 프로필 저장은 건드리지 않는다.
**수업이 끝나는 순간 저장한다.** 첫 전투 도중에 폰을 내려놓는 사람이야말로
다음에 켰을 때 걷는 법부터 다시 들으면 안 되는 사람이다.

시작 화면에 `조작 다시 배우기` 버튼. 하나라도 배웠으면 나온다.
전부 배워야 나오게 하지 않은 이유는, 보스 수업은 2분을 버틴 판이 있어야 끝나는데
폰을 남에게 넘겨주는 데 그걸 요구할 수 없기 때문이다.

### 검증

- 전투 검사 **53개 통과** (49 → 53).
- Unity 소스 컴파일(실제 Unity 6000.3.24f1 DLL 기준, Assets/Scripts + Assets/Editor) 경고 0 / 오류 0.
- 공통 전투 코어 변경 없음. 실험실 회귀 검사 불필요.

### APK 크기 — 개발 빌드는 전달 한도를 넘는다

0.15.0 개발 APK는 **31.2 MiB**로, 대화로 파일을 전달할 때의 30 MiB 한도를 넘어 전달에 실패했다.
직전 0.14.0 개발 APK는 22.4 MB였다. 설정은 그대로다(`stripEngineCode: 1`, `AndroidTargetArchitectures: 2` = ARM64 단독),
네이티브 라이브러리도 정상 압축돼 있다(libunity.so 24MB → 9.3MB). **9 MB가 늘어난 이유는 규명하지 못했다.**

같은 커밋을 `BuildOptions.None`으로 빌드하면 **16.7 MB**다.

| | 개발 빌드 | 릴리스 빌드 |
